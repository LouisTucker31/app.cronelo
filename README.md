# Cronelo

A project planner (timeline, list, calendar, board) that signs in and syncs through Supabase.
Plain HTML, CSS and JavaScript with no build step.

This repo is the app only. A separate marketing website advertises it and links to the app's
sign-up and sign-in screens: `#signup` opens "Create your account", anything else opens "Sign in"
(for example `https://app.yourdomain.com/#signup`). The app is kept out of search results
(`noindex` in `index.html`, and `X-Robots-Tag` in `_headers`); the website does the SEO.

- `index.html`: the page
- Addresses: a project opens at `/<its name>` (e.g. `/ex-hailstorm`); Cronelo, the home screen,
  is `/`. There's deliberately no `404.html`: without one, Cloudflare Pages serves `index.html` for
  any address that isn't a file, and the app reads the address (`js/app/core.js`). An address
  naming no project shows Cronelo. Because `index.html` can load at any address, it links to its
  files by full path (`/js/…`, `/css/…`). Adding a top-level `404.html` would break project links.
- `privacy.html`, `terms.html`: the privacy policy and terms of use, linked from the sign-in screen and the profile popup. Update the date at the top of each when they change.
- `css/`: `styles.css` (colour tokens at the top), `fonts.css`, and `legal.css` for the two pages above
- `js/early.js`: runs in `<head>` before the page draws (theme, framing check)
- `js/shared.js`: storage keys and helpers, HTML escaping
- `js/cloud.js`: sign-in, syncing, and loading the app
- `js/app/*.js`: the app, loaded in order by `js/cloud.js` (the list is `APP_FILES` there)
- `supabase/schema.sql`: the database table, its row level security and limits
- `_headers`: HTTP security headers for hosts that support them
- `manifest.webmanifest` and `assets/icon-*.png`, `assets/apple-touch-icon.png`: so the app can be
  added to a phone's home screen. `icon-any-*` are rounded tiles for desktops; `icon-192`/`icon-512`
  are full squares for phones, which crop them to their own shape (the C sits well inside the safe area)

To run it locally, serve the folder over HTTP (for example `npx serve .`) and open it in a browser.

## Hosting and security headers

Three security headers are missing while the site is on GitHub Pages, which can't send custom
headers: `X-Content-Type-Options`, `Permissions-Policy`, and `frame-ancestors`. They're all in
`_headers`, which Cloudflare Pages and Netlify apply automatically (both deploy from this repo, no
build command, output directory `/`).

The app is at https://app.cronelo.co.uk, on Cloudflare Pages (project `app-cronelo`, deploys
every push to `main`), with all the headers in `_headers` (checked 10 November 2026). The old
address `app-cronelo.pages.dev` forwards to it with a Cloudflare Bulk Redirect. GitHub Pages is
no longer used: the app links to its files from the site root, which GitHub Pages (under
`/app.cronelo/`) can't serve. Account emails are sent from no-reply@cronelo.co.uk through Resend (Supabase
custom SMTP).

Cloudflare Pages serves `privacy.html` at `/privacy` (it redirects); links to either work.

On GitHub Pages, the rest is covered without headers:

- **Content-Security-Policy** is set with a `<meta>` tag in `index.html`.
- **Referrer-Policy** is set with `<meta name="referrer">`.
- **Framing**: `js/early.js` hides the page when it's inside another site's frame. The app needs
  JavaScript, so a frame that blocks scripts gets nothing usable either.
- **HTTPS and HSTS** come from GitHub Pages itself.

After any hosting change, check the live headers with https://securityheaders.com.
(Mozilla's HTTP Observatory only scans a domain's root, so it can't grade a GitHub Pages
project site under `/workspace/`.)

## The Supabase library

`index.html` loads `@supabase/supabase-js` 2.118.0 from jsDelivr with an `integrity` hash, so a
changed file is refused. It's the published `dist/umd/supabase.js` (jsDelivr's `.min.js` is
regenerated by jsDelivr and its hash isn't stable).

To upgrade, change the version in three places, all of which must match: the `<script>` `src`
and `integrity` in `index.html`, the CSP `script-src` in `index.html`, and the CSP in `_headers`.
The hash is the SHA-384 of the exact file:
`curl -s https://cdn.jsdelivr.net/npm/@supabase/supabase-js@VERSION/dist/umd/supabase.js | openssl dgst -sha384 -binary | openssl base64 -A`

Check the version for known vulnerabilities before each release (https://osv.dev, or the
GitHub advisory database for `@supabase/supabase-js` and `@supabase/auth-js`).
Last checked: 30 October 2026, 2.118.0, no known advisories.

## Supabase settings

The URL and anon key in `js/cloud.js` are public by design; row level security in
`supabase/schema.sql` keeps each person's rows to themselves. Never put the `service_role` key
in this repo.

Apply `supabase/schema.sql` in the Supabase SQL editor after changing it. It's safe to run again.

In the dashboard, under Authentication:

- **Passwords**: minimum length 8 (the app asks for 8), and leaked password protection on.
- **URL configuration**: Site URL and Redirect URLs list only the address the app is served from.
  Sign-up, confirmation and password reset emails link back to it.
- **Email confirmation** stays on.

Bot protection (Cloudflare Turnstile, free):

1. In the Cloudflare dashboard, go to Turnstile, add a widget for the app's domain (add `localhost`
   too for testing), mode **Managed**. Copy the site key and the secret key.
2. Put the site key in `TURNSTILE_SITE_KEY` in `js/cloud.js`, and deploy.
3. Only then, in Supabase: Authentication → Attack Protection (Bot and Abuse Protection) → turn on
   CAPTCHA protection, provider Turnstile, and paste the secret key. Doing this before step 2 is live
   stops everyone signing in.

The Turnstile script can't be pinned with an `integrity` hash like the Supabase library, because
Cloudflare updates it in place; the CSP allows only `https://challenges.cloudflare.com`.

Signed-out visitors can't read `user_data` and see no storage buckets (checked 30 October 2026).
Any new table needs row level security turned on before it holds data.

## Error reports and deleting accounts

`supabase/schema.sql` also sets up:

- `app_errors`: errors people hit in the app (message, code location, page, browser; never their
  plans). Read them in Table Editor → `app_errors`. People can add reports but not read any. At most
  10 per visit and 200 per account a day; reports older than 90 days are cleared automatically.
- `delete_my_account()`: what Profile → Delete account calls. It deletes the caller's own sign-in,
  and with it all their rows.

Run the file again in the SQL editor after pulling these changes, or neither will work.
